# GitHub BIM可用几何内核（Rust为主，对比truck‑cad）

> truck‑cad：Rust原生BRep，NURBS、布尔、放样、偏移、STEP读写，MIT/Apache‑2.0，目前Rust生态完成度最高的原生CAD内核，适合参数化隧道、管廊这类放样带洞口场景。

## Rust原生BRep内核（可以直接做参数化BIM几何）

### 1. brepkit（andymai/brepkit）

- GitHub：https://github.com/andymai/brepkit
- 能力：完整B‑Rep，NURBS曲线曲面、放样(sweep)、布尔运算、倒角、偏移；STEP/3MF/STL导入导出；支持WASM+本地Rust双运行；拓扑拾取、体积测量、几何修复。
- 许可：3.0+ **AGPL‑3.0，商业产品需要购买商业授权**；2.x版本是MIT‑Apache。
- 现状：活跃迭代；适合参数化隧道、曲线路径放样开洞口；比truck‑cad的布尔鲁棒性更好，但许可对闭源项目不友好。
- 短板：复杂NURBS曲面的性能弱于OCCT；大模型三角化还有优化空间。

### 2. NURBS_BREP_kernel（BREP_kernel）

- GitHub：https://github.com/mmiscool/NURBS_BREP_kernel
- 能力：纯Rust BRep，解析曲面（平面、圆柱、圆锥、球面）、实体分割、基础布尔；自带wgpu渲染+拾取；egui示例程序。
- 许可：MIT/Apache‑2.0
- 现状：0.5版本，**偏实验**；基础实体够用，复杂NURBS放样、倒角缺失；适合原型验证，不建议直接生产BIM。

### 3. manifold‑rust（网格布尔内核，不是BRep）

- GitHub：https://github.com/hangxie/manifold‑rust
- 定位：**流形网格布尔内核，没有BRep拓扑**，只有三角面片；不能保存参数化信息，做完就变成网格。
- 适合：生成预览网格、快速CSG；**不适合BIM参数化编辑（不能后续修改路径、洞口）**。
- 优势：布尔非常稳定，处理脏几何容错强；MIT。

## Rust包装OCCT（复用工业级C++内核）

### occt‑wasm

- GitHub：https://github.com/andymai/occt‑wasm
- 原理：OCCT预编译WASM包，Rust通过wasmtime调用，不需要本地编译C++/CMake。
- 能力：完整OCCT全部能力：高级放样、变截面扫掠、复杂NURBS、强大布尔、几何修复、STEP/IGES；电缆隧道曲线路径+开洞完全hold住。
- 许可：OCCT底层LGPL，wrapper MIT/Apache；**闭源商业软件可以使用**。
- 缺点：WASM二进制包体积大；跨调用有序列化开销；不是原生Rust，调试栈麻烦。

## BIM专用Rust库（侧重IFC读写，几何内核依赖上面）

### ifc‑lite

- GitHub：https://github.com/LTplus‑AG/ifc‑lite
- 定位：IFC解析/序列化/查询；**本身不实现完整BRep建模内核**，可以对接truck‑cad / brepkit / occt‑wasm输出几何写入IFC。
- 支持IFC4X3、IFC5、BCF、IDS；Rust core + TS前端，Tauri/浏览器均可运行。

## 非Rust成熟开源BRep内核（参考，你的PVBIM项目可以FFI调用）

1. **OpenCASCADE(OCCT)** C++，行业事实标准，LGPL；电缆隧道变截面放样、洞口布尔修复最稳；缺点编译重，API繁琐。
2. **Manifold** C++，网格布尔；无BRep拓扑。
3. **IfcOpenShell** C++(基于OCCT)，专门IFC几何转换。

# 核心结论

你现在遇到的三个短板，**是所有Rust原生BRep库（truck-cad / brepkit）共同的短板，不是某个库的bug**；Revit/OCCT有专门的**几何层面轮廓提取 + HLR隐藏线消隐**，不是GPU深度缓冲。

> GPU深度缓冲方案：只能做屏幕空间的像素级消隐，**不能导出矢量PDF/DXF的2D工程图**；也提取不出曲面silhouette轮廓线。 下面分「方案优先级」给出解决办法，适配你的PVBIM（电缆隧道BIM）场景。

## 问题拆解回顾

1. ❌ HLR隐藏线：GPU深度缓冲是像素级，得不到矢量线段；不能输出矢量工程图
2. ❌ Silhouette轮廓线（圆柱/曲面侧影母线）：BRep的边只是拓扑边，**曲面光滑过渡的轮廓不属于BRep边**，原生BRep内核不会自动生成
3. ❌ 线框样式：没有粗线、管状线，只有1px屏幕像素线

# 方案1：OCCT做几何侧轮廓+HLR计算（最稳妥，对标Revit工程图，推荐）

OCCT本身自带成熟模块：

- `BRepAlgoAPI_Silhouette`：提取任意视角下实体的silhouette轮廓线（圆柱的侧母线）
- `HLRAlgo_Projector` + `HLR_BRepAlgoAPI`：**几何层面的隐藏线移除算法**，输出纯矢量线段，和GPU无关
- 输出结果：2D矢量线段集合，可以导出DXF/PDF/SVG工程图，支持粗线、虚线、隐藏线分层

### 两种集成方式（适配你的Rust栈）

1. **FFI调用原生OCCT（C++）**：Rust主线程把BRep模型（STEP）传给OCCT，OCCT执行投影+轮廓提取+HLR，返回矢量线段数组。适合桌面Tauri程序。
2. **occt-wasm**：WASM版本OCCT，Rust通过wasmtime调用；适合跨平台，但是大模型会有性能开销。

> 工作流（PVBIM） `truck-cad 生成BRep实体 → 导出STEP → OCCT(wasm/FFI)做投影+轮廓+HLR消隐 → 返回2D矢量线集合 → Rust前端渲染矢量线，设置粗线/虚线/隐藏线分层 → 导出DXF/SVG/PDF`

✅优点：完全工业级，和Revit底层逻辑一致；silhouette、HLR全部搞定 ⚠️缺点：需要维护OCCT依赖；跨语言调用；STEP序列化/反序列化有开销

## 方案2：纯Rust自研几何轮廓 + HLR（长期路线，工作量巨大）

分成两个独立模块：

1. Silhouette轮廓提取

    原理：遍历BRep所有曲面，对于给定相机方向，求曲面

   视线相切的轮廓边

   。

   - 平面：无silhouette

   - 圆柱、圆锥、NURBS曲面：求解视线与曲面的相切点，拼接成轮廓线

     > 难点：NURBS曲面求相切方程，数值稳定性、曲面裂缝、离散奇点；BRep拓扑缝合。

2. HLR隐藏线算法（几何级，不是屏幕空间）

    经典算法：

   Atherton–Weiler

    或者基于BRep的HLR（OCCT HLR的论文基础） 流程：

   1. 把3D所有边（BRep边+silhouette轮廓线）投影到2D平面
   2. 对每一条投影线段，求它是否被实体面遮挡
   3. 线段切割成「可见段」和「隐藏段」，分层输出矢量线条

✅优点：完全Rust原生，无C++依赖，和truck-cad深度集成 ⚠️缺点：**工程量极大**。单纯写HLR+silhouette，人月级别；曲面NURBS的轮廓求解非常容易数值崩坏，电缆隧道的复杂放样曲面坑很多。适合长期迭代，不适合现阶段PVBIM快速落地。

## 方案3：屏幕空间后处理（低成本，只能预览，**不能导出矢量工程图**）

适合只做3D视口里的预览，**无法输出DXF矢量图**，只能解决“视图看起来有轮廓”。

### 3.1 轮廓描边（卡通描边/Sobel）WGPU后处理

- Wgpu渲染实体，生成深度+法向纹理

- 后处理着色器做边缘检测：深度突变 / 法向突变，提取像素轮廓，叠加黑色粗描边

- 可以做出圆柱侧面轮廓线视觉效果

  > 局限：像素级，屏幕分辨率相关；放大锯齿；**不是矢量线段，不能导出工程图**

### 3.2 粗线/管状线问题解决（GPU渲染层）

原生1px线段的替代方案： 不要直接渲染GL_LINES，改用**几何着色器把线段扩展成矩形条带（screen-space quads）**，或者用**管线生成管状圆柱（cylinder）**来表达线框。

- wgpu生态：`lyon`、`egui_plot`、`puffin`或者自己写几何shader；
- 效果：屏幕空间恒定粗细的粗线，不受缩放影响；也可以做管状线框。

> 这个方案只能解决**3D预览视觉效果**，不能解决HLR矢量工程图需求。如果你不需要导出2D施工图，只做3D视图预览，这个方案最轻量。

## 方案4：第三方矢量投影库（中间备选）

比如`OpenCascade`之外：

- `cglib`、`libfive`：弱，没有完整BRep silhouette和HLR
- `ParaView`：VTK，有轮廓提取，但VTK的HLR能力一般，适合可视化，不适合BIM施工图矢量输出

### 场景A：你需要输出2D矢量施工图（DXF/PDF，和Revit出图对等）【电缆隧道BIM大概率要】

👉 **首选：truck-cad做参数化建模，OCCT（FFI/occt-wasm）专门承担轮廓提取 + HLR隐藏线计算**

- 建模、参数化、BIM逻辑、IFC输出：Rust(truck-cad + ifc-lite)

### 场景B：只做3D可视化预览，**不需要导出矢量工程图**

👉 不用OCCT。直接wgpu后处理描边 + screen-space粗线几何着色器，快速实现视觉轮廓效果。 缺点：不能导出CAD矢量图纸。

# 补充：粗线/管状线独立实现思路（Rust+wgpu）

1. 屏幕空间粗线：线段的两个端点，根据相机方向计算垂直偏移，生成矩形四边形，wgpu绘制。线宽固定屏幕像素，不会因为缩放粗细变化。
2. 管状线（3D空间圆柱管线）：把每条边生成细圆柱BRep实体，交给truck-cad；适合BIM管线、隧道轴线可视化，代价是几何变多。

# 取舍总结

Revit的核心优势之一就是**内置成熟几何级Silhouette提取 + HLR隐藏线矢量投影**，这一块不是简单渲染问题，属于**几何算法模块**，不是渲染器模块。 Rust原生BRep库（truck-cad）现阶段都没实现这套，短期内自己完整实现成本极高。 **工程落地最优解：建模用truck-cad，出矢量工程图交给OCCT。**

# 一句话结论

✅ **occt‑wasm 可以搞定前两个核心问题（HLR矢量隐藏线 + Silhouette曲面轮廓线），完全对标Revit工程图的几何级投影；** ⚠️ **第三个问题（粗线/管状线）occt‑wasm本身不做渲染管线，它只输出矢量线段数据，粗线绘制交给Rust/wgpu上层处理。**

## 逐条拆解你的三个痛点

### 1. ✅ HLR隐藏线（几何级，输出矢量线段，不是GPU深度缓冲）

occt-wasm完整暴露OCCT原生的`HLRBRep_Algo` / `HLRBRep_PolyAlgo`，就是OCCT官方的几何隐藏线移除算法

- 输入：BRep实体 + 投影相机（投影方向、视锥）

- 输出：

  分类后的2D矢量线段集合

  ，区分：

  - 可见实线（Visible）
  - 隐藏虚线（Hidden）
  - 轮廓线Outline（silhouette）

- 本质：

  几何计算，不是像素深度测试

  ，得到的是数学线段，

  可以导出DXF/SVG/PDF矢量工程图

  ，这正是truck‑cad做不到的。

  > 对应Revit的工程图投影逻辑。

### 2. ✅ Silhouette轮廓线（圆柱侧面素线这类曲面轮廓）

OCCT HLR模块原生就会计算`Outline Edges`，专门处理光滑曲面在当前视角的相切轮廓（圆柱、圆锥、NURBS放样曲面的侧轮廓母线）

- 这些轮廓**不属于BRep拓扑边**，是HLR算法在投影时动态求解生成；

- occt-wasm在HLR计算后，可以单独把这一类轮廓边提取出来，和普通BRep边界边合并成一套完整工程图线集合。

  > 电缆隧道变截面放样曲面，任意视角下的外轮廓线都可以拿到。

> 注意：OCCT有两套HLR：
>
> - `HLRBRep_Algo`：基于精确BRep几何，精度高，但慢；
> - `HLRBRep_PolyAlgo`：基于三角离散后的多面体，速度快，工程图常用； occt-wasm两者都可用。

### 3. ⚠️ 粗线 / 管状线：occt-wasm**不负责绘制**，只输出线段

OCCT内核（occt-wasm）只输出**几何线段数据（起点、终点、线段类型）**，**没有内置的粗线渲染、屏幕空间粗矩形条、3D管状圆柱生成**。

- 它返回的是抽象几何线，不是像素；
- 线宽、线型（实线/虚线）、粗线样式，**由你Rust端渲染层（egui/lyon/wgpu）来绘制**；
- 两种实现方案：
  1. **2D矢量工程图（DXF/SVG）**：拿到occt-wasm输出的线段，在导出时直接写入DXF的`LWPOLYLINE`，设置线宽；SVG里设置`stroke-width`；最简单。
  2. **3D视口里预览粗线**：wgpu几何着色器把线段扩展成屏幕空间矩形条，或者生成细圆柱BRep实体（可以交给occt-wasm生成管状BRep）。

## 完整工作流（适配你的PVBIM）

```
truck-cad 生成隧道BRep实体
        ↓ 导出BREP/STEP
occt-wasm（wasmtime在Rust进程内运行）
    ├─ HLR投影计算
    ├─ 提取：普通边 + Silhouette轮廓边
    └─ 分类：可见线段 / 隐藏线段
        ↓ 返回Rust：一组2D矢量线段（带类型标记）
Rust上层：
    ├─ Egui/Lyon渲染2D工程图：设置粗线、虚线分层
    ├─ 导出SVG/DXF/PDF矢量图纸
    └─ 可选：wgpu 3D视口预览粗线框
```

## 局限与坑（occt-wasm）

1. **WASM性能开销**：大型隧道装配体，HLR计算会明显慢于原生C++ OCCT；适合交互式单构件/局部视图，超大装配会卡顿；可以后台wasmworker异步计算。
2. **HLR本身的数值稳定性**：OCCT HLR遇到退化曲面、微小缝隙、薄壳，偶尔会出现轮廓断裂、线段碎段，需要做线段合并/容差后处理（Rust端写简单后处理）。
3. **API边界**：occt-wasm暴露HLR，但不是所有底层C++ HLR参数都完全开放；复杂调参（容差、精度控制）需要查occt-wasm的spec。
4. **许可**：底层OCCT是LGPL；occt-wasm包装层MIT/Apache，**闭源商业软件可以使用**（动态链接LGPL，静态链接需要留意LGPL条款）。

## 对比方案取舍

- 只做3D预览：truck-cad + wgpu后处理描边（无法矢量出图）
- **要输出矢量工程图（DXF/SVG，带曲面轮廓+隐藏线）：truck-cad + occt-wasm，就是最优方案**

# cadrum vs occt‑wasm 完整对比（面向你的PVBIM，重点关注HLR、silhouette、构建、许可、性能）

> 共同点：两者都是Rust封装OCCT；**都完整支持OCCT的`HLRBRep_Algo`，可以做几何级隐藏线消隐、silhouette曲面轮廓提取，解决你前面Revit出图的两大痛点**。 区别在底层运行方式、构建依赖、API暴露范围、许可风险、跨平台打包。

## 核心架构差异

### occt‑wasm

- 原理：OCCT预先编译为WASI‑Wasm二进制包，嵌入crate，Rust本地通过**wasmtime虚拟机**加载运行OCCT，不是原生CPU机器码。
- 构建：**不需要本地C++编译器、CMake，不需要编译OCCT源码**，直接`cargo add occt‑wasm`即可使用。
- 内存：OCCT全部对象驻留在Wasm沙堆；Rust侧只有`ShapeHandle`句柄，不能直接访问C++对象内存。
- HLR：已经封装HLR隐藏线投影，可输出SVG矢量，可提取可见线段、隐藏线段、silhouette轮廓线，满足BIM工程图需求。
- 许可：Rust封装层 MIT‑Apache‑2.0；底层OCCT LGPL‑2.1；wasmtime动态加载Wasm模块，**属于动态链接，闭源商业软件合规风险低**。

### cadrum

- 原理：**原生FFI绑定OCCT**；编译阶段自动下载OCCT源码，本地C++编译器编译OCCT，静态链接进最终exe，直接CPU原生执行，没有虚拟机中间层。
- 构建：本机**必须安装C++编译器(MSVC/GCC/Clang)+CMake**；CI服务器也要配置C++编译环境，否则编译失败。
- 内存：Rust侧包装OCCT C++对象，直接原生指针访问。
- HLR：自带`export_svg_with_hlr`，内部调用OCCT原生HLR算法，输出带隐藏线、轮廓的SVG矢量图，silhouette可用。
- 许可：Rust封装层MIT；OCCT底层LGPL‑2.1；**cadrum是静态链接OCCT**，分发闭源软件时，必须满足LGPL静态链接条款：向用户提供OCCT重编译替换手段，合规负担更高。

## 针对你的PVBIM项目（truck‑cad为主建模，OCCT只做HLR+轮廓+复杂布尔）选型建议

### 场景1：Windows桌面商业软件（Tauri/Avalonia，闭源分发，优先打包简单）👉 **occt‑wasm**

1. 不需要在CI搭建C++编译环境；cargo直接构建；
2. 许可风险低，静态链接带来的LGPL合规压力小；
3. 你的用途**不是实时高频几何交互**，是后台执行HLR投影、轮廓提取、少量修复运算；2倍性能开销完全可以接受；
4. 缺点：极冷门OCCT底层API拿不到；遇到边界case需要改occt‑wasm的facade。

> 工作流：truck‑cad生成BRep → 导出STEP/BRep → occt‑wasm加载，执行HLR，提取可见/隐藏/silhouette矢量线段 → Rust上层渲染/导出DXF/SVG。

### 场景2：科研原型，需要深度调用OCCT底层API，追求极致性能，不关心打包复杂度👉 **cadrum**

1. 原生OCCT性能最优；调试C++崩溃方便；可以访问OCCT几乎全部API；
2. 代价：CI/开发机必须维护C++编译环境；闭源分发要处理LGPL静态链接合规。

### 避坑提醒

1. 两者**都不处理粗线/管状线**：仅输出矢量线段；线宽、线型、虚线绘制仍然由Rust上层（lyon/egui/wgpu/DXF导出层）完成。
2. occt‑wasm不要频繁反复新建`OcctKernel`；**全局复用一个实例**，实例初始化开销很大。
3. HLR计算大装配体，不管哪个库，建议放到后台线程异步计算，不要阻塞UI。

## 取舍总结

> 如果你做面向分发的桌面BIM软件，**优先occt‑wasm**，规避C++编译链和LGPL静态链接合规麻烦； 如果你是内部原型、科研，要深挖OCCT底层API，选cadrum。

# SketchUp(Mesh)能不能用来做BIM软件 + Rust对应SDK

> 核心结论：**纯Mesh（SketchUp这套多边形面‑边模型）不能完整做工程级BIM创作软件；但可以做BIM的**查看、校验、轻量化流转、预览工具**；BIM的“信息（语义属性）”可以补上，但**几何工程能力存在硬缺陷**。

## 一、SketchUp Mesh模式做BIM的优缺点（电力GIM场景）

### ✅ 优点

1. 上手简单，模型交互快，渲染开销低；
2. 可以附加**语义属性**（设备ID、专业、阶段、参数），几何Mesh + 外部业务元数据 = 可以满足**查看、展示、成果归档、可视化校验**；
3. GIM、IFC可以输出三角面片模式，Mesh可以作为**交付/预览形态**。

### ❌ 硬短板（电力设计致命，工程BIM创作绕不开）

1. **没有解析曲面，全部是离散逼近** 圆柱绝缘子、母线、钢管杆全部拆成小多边形；剖切得到锯齿轮廓，**无法做精确截面计算、土方、面积、体积精确计算**，计算结果是近似值，会累计误差。
2. **网格布尔不稳定** SketchUp Solid‑Tools是网格布尔；微小公差就出现缝隙、非流形，电力设备装配、开孔、干涉检查可靠性远不如B‑Rep。
3. **不能参数化回滚编辑** 圆柱做完布尔之后，不再保留“圆柱半径”原始定义；改尺寸只能重新建模。B‑Rep内核可以保留原始几何定义，修改参数直接重算。
4. **和国内电力标准GIM冲突** GIM的DEV原始模型层，**要求优先保存解析B‑Rep实体，再三角化得到PHM/MOD显示网格**；如果源头只有Mesh，就没有原始解析几何，只能填充MOD显示层，DEV层缺失，不符合DL/T标准要求。

> 区分两个概念：
>
> - **BIM查看/校验/流转工具**：Mesh够用；
> - **BIM正向设计创作软件（建模出图、精确工程计算）**：纯Mesh不行，必须B‑Rep。

> SketchUp本身做建筑概念方案可以靠插件补语义，但工业/电力工程级正向设计不适合作为底层几何内核。

## 二、Rust 有没有类似 SketchUp 的Mesh建模SDK

### 1. Mesh多边形建模（对标SketchUp几何层：边‑平面‑面，网格布尔）

| crate                | 能力说明                                                     |
| -------------------- | ------------------------------------------------------------ |
| **csgrs**            | 基于BSP树做Mesh CSG布尔；OpenSCAD风格，多边形网格布尔；适合生成、处理闭合多边形壳体，类似SketchUp SolidTools逻辑 |
| `nalgebra + parry3d` | 线性代数 + 碰撞检测；没有建模编辑能力，提供相交、包围盒、距离计算；用来做干涉检查 |
| `earclip`            | 多边形三角剖分；做面分割                                     |
| `openskp`            | **Rust读取SketchUp `.skp`文件**，读取组件、层级、面、边、材质、自定义属性；仅读，**不支持写skp，不能做交互式编辑**，适合做解析校验工具 |

> ⚠️ 现状：Rust生态**没有开箱即用、完整交互式多边形编辑内核（完整复刻SketchUp GUI建模逻辑）**。csgrs偏向程序化生成，不是交互式拖拽编辑。 如果你要做类似SketchUp的GUI编辑器，需要自己实现：选择、推拉、偏移、裁剪、组件实例，工作量巨大。

### 2. Rust B‑Rep内核（真正工程CAD/BIM内核，推荐电力场景）

> 如果你做**正向设计BIM工具，不要走纯Mesh路线，优先B‑Rep**，运行时可以随时Tessellate三角化成Mesh用于渲染。

1. **brepkit**：纯Rust从零实现B‑Rep；支持解析曲面（平面/圆柱/球面/NURBS）、布尔运算、STEP读写、导出三角Mesh；可编译WASM，Tauri桌面、Web都能用。
2. 绑定OpenCASCADE：`opencascade‑rs`，把C++ OCCT做Rust FFI包装；工业成熟B‑Rep内核，体量很大，编译部署重。

> 最佳分层架构（适配你的GIM标准）： **底层B‑Rep（brepkit/OCCT）保存原始解析几何 → 按需三角化输出Mesh给渲染；业务元数据存PostgreSQL；输出GIM时DEV存B‑Rep，MOD/PHM存三角网格**。

- 使用 `openskp` 读取skp；

- brepkit / occt‑rs 解析B‑Rep；

  > 只做解析校验，**不做交互式建模编辑器**，避开巨大GUI建模工作量。

### 场景B：如果未来要做轻量建模工具

1. **不要以纯Mesh作为主存储**；主存储B‑Rep，渲染输出Mesh。
2. 不要复刻SketchUp交互内核（开发成本极高）；优先做**参数化构件库**：输入杆塔、绝缘子参数，程序生成B‑Rep实体，自动三角化预览。

# 结论先行

**完全可以做出可用的BIM软件，但要分清：「能跑原型/轻量化BIM」 vs 「对标Revit完整内核」。** 你说的前提很关键：**不需要复杂高阶曲面布尔**，只做建筑常用几何体（拉伸、旋转、放样、简单圆角、壳体、实体差/交/并，建筑直墙、楼板、梁柱），Rust+Brep几何内核+wgpu渲染是非常合适的路线。

> 一句话边界：建筑BIM绝大多数构件本身就是**简单BREP实体**，NURBS高阶曲面极少；难点不在曲面布尔，而在**BIM数据语义、构件参数化、拓扑持久化、构件关联、大场景渲染**。

## 一、Rust 可用BREP几何库盘点（对应你的场景）

### 1. `rust-geo` 系列：侧重2D，**不适合3D Brep实体**

只是平面几何、多边形，没有3D拓扑、实体布尔，只能做轮廓，排除。

### 2. `salvo3d` / `cadlab`（社区原生Rust Brep）

- 纯Rust实现BREP边界表示，支持面、环、边、顶点拓扑；
- 支持拉伸、旋转、基础布尔运算（并差交）；
- ✅ 优势：内存安全、可编译WASM、与wgpu天然适配；
- ❌ 短板：**布尔鲁棒性弱于OCCT**，微小公差、共面、重叠面很容易拓扑破损；没有复杂NURBS，刚好匹配你“不需要麻烦曲面布尔”的需求；
- 定位：**轻量化CAD/BIM原型首选**。

### 3. `parry3d`（rapier作者）

- 不是BREP，是碰撞几何（三角网格、凸包）；
- 适合物理/碰撞，**不能做参数化实体BIM**；网格丢失拓扑，不能回退编辑构件，不适合BIM内核。

### 4. `occt-rs`（OCCT绑定）

- 把C++ OpenCASCADE绑到Rust；BREP能力最强，布尔、NURBS齐全；

- ❌ 缺点：底层仍是C++，内存安全优势大打折扣，编译部署麻烦，有FFI开销；

  > 如果你目标是**纯Rust内核**，就不选这个；如果只是要最强几何能力，可以选。

### 5. `cortex-rs`、`truck`（Truck CAD，重点！）

# 核心选型推荐（纯Rust BREP + wgpu）

1. **TruckCAD（monstertruck）**：最成熟的纯Rust BREP，原生NURBS、BREP拓扑、布尔运算、STEP读写，自带wgpu渲染模块；建筑直构件、开孔布尔完全够用，社区活跃。

## 二、BIM软件的真正难点（**不是几何布尔，是下面这些**）

你说不需要复杂曲面布尔，这个假设对建筑BIM成立（墙、板、柱、门窗洞都是简单实体差集），但BIM远不止几何：

1. **IFC语义层（重中之重）** BREP只是**形状表达**；BIM核心是`IfcWall`、`IfcWindow`、属性集、空间关系、构件关联、洞口关系、空间分区。 Rust生态：`ifclite` 是高质量Rust IFC解析库，可以读IFC4，支持IfcBooleanClippingResult（门窗开孔布尔），可以和上面BREP内核打通。

   > 几何内核只回答：**长啥样**；IFC层回答：**它是什么构件、属性、关联关系**。

2. **参数化构件与约束、特征树** 墙体拉伸、轮廓、偏移、门窗联动剪切；修改墙厚度，洞口自动跟随。 原生Rust BREP库目前**没有成熟的参数化特征树**（OCCT有），这部分要自己写：特征栈、持久化拓扑快照、回滚撤销。

3. **拓扑持久化 + Undo/Redo** BREP拓扑一旦布尔后直接销毁原始拓扑，BIM需要保留**建模历史**。Rust的所有权模型在这里有利有弊，需要Handle/ID引用而不是直接引用拓扑对象。

4. **大场景性能** 一栋建筑几十万构件，不能每帧Tessellate；要缓存三角网格、wgpu instanced渲染、LOD、视锥裁剪、空间索引（AABB树）。 wgpu非常适合，实例渲染可以一次性绘制成千上万个梁柱构件。

5. **工程校验：碰撞检查、面积体积、截面剖切** BREP内核提供几何测量；剖切可以在BREP层面做（精确截面线），也可以wgpu片段着色器做快速剖切（仅可视化）。

6. **文件持久化**

- 私有工程文件：序列化BREP拓扑+IFC构件语义；
- 交换：STEP（几何）+ IFC（BIM语义）；Truck、brepkit都支持STEP导出；ifclite读写IFC。

# 核心结论

**不需要额外引入完整独立CAD内核，但必须引入「三维BREP投影剖解 → 二维几何+约束」的一套管线；分两条路线：内核自带2D投影，或者自己搭建投影管线。** BIM出施工图本质不是“单独开一个CAD窗口画图”，而是：**从三维BIM模型，自动生成投影视图/剖面图 → 提取2D轮廓线、隐藏线、断面填充 → 再提供传统CAD式的2D编辑（画线、标注、文字、图层、块）**。

> 关键点区分两个概念：
>
> 1. **几何投影/消隐/剖切（从3D得到2D线框）**：这一步依赖BREP内核能力；
> 2. **2D矢量编辑、标注、DWG/DXF读写、图层/块/样式**：这是2D CAD绘图模块，可以独立，**不需要再套一套完整BREP三维内核**。

## 一、基于你选定栈：Rust + TruckCAD + wgpu 的方案拆解

TruckCAD（纯Rust BREP）本身就内置**BREP投影、轮廓提取、截面剖切线生成**，刚好解决第一步：

1. 对三维实体做正交投影（平面图、立面图）或者剖切（剖面图）；
2. 遍历BREP的边，区分**可见线 / 隐藏线**；
3. 生成2D的曲线集合（直线、圆弧、NURBS），输出二维几何图元。

⚠️ Truck**没有内置传统CAD 2D编辑系统**（没有标注、文字、块、图层、DXF/DWG、捕捉、修剪、延伸）。 这里有两个选择：

### 方案A：自建轻量2D矢量绘图模块（推荐，贴合PVBIM）

只做**二维图元容器+编辑工具**，不再引入三维BREP。 模块职责：

- 承载投影出来的2D几何（线、圆弧、多段线）；
- 2D编辑命令：画线、偏移、修剪、延伸、圆角、裁剪、对象捕捉；
- 注释系统：尺寸标注、标高、文字、填充、图框；
- 图层、颜色、线型、块定义；
- DXF导出（Rust生态：`dxf-rs`，读写DXF；DWG比较麻烦，DWG是闭源，一般走DXF中转）。

> 架构分层（新增2D模块，不替换三维BREP）

```
flowchart TB
    A[BIM三维层<br/>Truck BREP + IFC] -->|剖切/正交投影+消隐| B[2D几何提取<br/>轮廓、断面线、隐藏线]
    B --> C[2D矢量绘图引擎<br/>自建：图元、图层、标注、捕捉、编辑命令]
    C --> D[2D视口渲染<br/>wgpu共享渲染后端，复用egui/Tauri UI]
    C --> E[DXF导出 dxf-rs]
```

✅ 优点：

- 三维/二维共用一套项目数据模型，**视图与BIM构件双向关联**：改三维墙体，图纸投影自动更新；
- 共享wgpu，不用引入另一个渲染器；
- 无额外重型几何内核依赖；
- 你可以控制“关联性”：2D标注绑定三维构件，修改3D自动驱动2D更新，这就是BIM图纸的核心（普通CAD做不到）。

❌ 代价： 2D CAD工具链工作量不小：对象捕捉、修剪/延伸、相交求交、尺寸标注引擎、线型、填充算法，都是工程活。

> 但**2D求交比3D BREP布尔简单非常多**，可以用轻量2D几何库辅助：`geo`、`lyon`、`kurbo`处理平面曲线求交。

### 方案B：引入独立2D CAD库作为子模块（复用轮子，减少开发量）

Rust生态可选的2D矢量CAD库，**只用来承载二维图纸，不带三维BREP**：

1. `cad-rs`：轻量2D CAD内核，图元、图层、DXF读写，基础编辑；适合直接接入投影输出的几何。
2. `euclid` + `kurbo`：基础平面几何、曲线、路径，适合底层搭建。
3. 备选：嵌入FreeCAD的2D Draft模块（不推荐）——FFI，引入C++依赖，破坏纯Rust目标。

> 避坑：**不要引入OCCT只为出2D图纸**。OCCT的2D投影/绘图很强，但一旦引入，你就回到FFI的复杂度，违背纯Rust内核初衷。

## 二、两种图纸模式（BIM软件都同时支持）

1. 关联视图（BIM自动视图）

    由3D模型生成，2D图元是

   派生出来的只读/半只读

   。修改三维构件，图纸自动刷新；可以在图纸上加注释、尺寸，但不能随意删除投影轮廓（删除会联动三维）。

   > 这是Revit、ArchiCAD的施工图模式。

2. **解耦的2D详图（传统CAD模式）** 把投影结果“炸成纯2D图元”，切断和三维模型关联，之后完全自由CAD编辑，用来画大样、节点详图。

## 三、DWG/DXF的现实问题

- DXF：开源，`dxf-rs` Rust库读写完全够用，出图交付首选；
- DWG：Autodesk闭源格式。Rust没有原生开源DWG读写库。 策略：导出DXF，用户用AutoCAD转DWG；或者未来调用ODA File Converter做离线转码（外部进程，不嵌入内核）。

## 四、一条很重要的技术取舍点：隐藏线消隐

单纯投影得到的线框会**所有线都显示，没有虚线隐藏线**，施工图不能直接用。 两个实现路线：

1. **BREP级精确消隐（Truck支持）**：遍历BREP拓扑，判断面遮挡，区分可见/隐藏边；精度高，但对复杂模型慢；适合建筑构件数量可控的场景。
2. **基于wgpu深度缓冲的图像空间消隐**：GPU生成深度图，反向提取轮廓。速度快，但几何不稳定，适合预览，**不能用于施工图出图**（精度不足，无法用于尺寸标注）。

> 施工图必须用BREP几何消隐，不能依赖GPU深度。

## 五、和你备选方案对比：C# + AnyCAD/OCCT

OCCT自带成熟的`ProjLib`投影、`HLR`隐藏线消隐、2D草图模块，**直接拿来生成工程视图**，省去你自己写BREP投影+消隐。代价是C#/C++FFI。 Rust Truck路线：投影/消隐已经有，但成熟度弱于OCCT HLR；你要自己封装视图管理、图纸页、视口、标注。

## 六、最简落地顺序（建议分阶段做，不要一次性写完整套CAD命令）

1. 第一阶段：只实现**模型剖切 + 正交投影 + 消隐**，输出2D线集合，渲染在2D视口，先不做编辑。 目标：三维墙体一键生成平面/立面线框。
2. 第二阶段：2D基础图元、图层、文字、尺寸标注引擎，DXF导出。
3. 第三阶段：2D编辑命令（画线、修剪、捕捉），支持详图模式。
4. 第四阶段：双向关联，三维改动驱动图纸刷新。

## 七、是否需要引入额外CAD库？一句话总结

# 如何在Rust中实现二维几何图元的标注、文字、块、图层、DXF/DWG、捕捉、修剪、延伸等功能？



# Rust 二维CAD模块完整实现路线（适配你的PVBIM：三维BREP投影出二维图纸）

> 核心前提：**二维系统不是独立CAD内核，是依附在你的Rust BREP三维几何之上的投影2D工作空间**；三维模型做剖切/投影 → 生成2D图元（线、圆弧、多段线）→ 在2D视口做标注、捕捉、修剪、图层、DXF导出。 DWG**不建议原生写解析器**（格式闭源、版权复杂），优先DXF，DWG走外部转换。

## 一、模块拆分（Rust crate划分）

```
pvbim_2d
├── pvbim_2d_core          # 图元、图层、块、标注数据模型
├── pvbim_2d_geom          # 2D几何：点/线/弧/样条，修剪、延伸、求交、偏移
├── pvbim_2d_snap          # 对象捕捉逻辑（端点、中点、垂足、交点、圆心）
├── pvbim_2d_hlr           # 隐藏线计算（三维BREP投影HLR，生成2D消隐线）
├── pvbim_2d_text          # 文字、多行文字、字体度量
├── pvbim_2d_dxf           # DXF R12/R2000 读写
├── pvbim_2d_render_wgpu   # wgpu绘制2D视口（线条、标注、文字、图层显隐）
└── pvbim_2d_edit          # 编辑命令：trim / extend / fillet / offset / move
```

## 二、各功能点实现方案 & Rust库选型

### 1. 基础数据模型（图层、块、图元、标注）

直接在Rust定义强类型结构体，不用依赖外部几何库：

```
// 简化示例
#[derive(Debug, Clone)]
pub struct Layer {
    pub name: String,
    pub color: [u8;4],
    pub line_weight: f32,
    pub visible: bool,
    pub locked: bool,
}

pub enum Entity2d {
    Line(Line2d),
    Arc(Arc2d),
    Polyline(Polyline2d),
    Dimension(Dimension), // 标注：线性、对齐、半径、直径
    Text(Text),
    BlockRef(BlockReference), // 块引用
}
```

- **块Block**：BlockDefinition（内部图元集合）+ BlockRef（插入点、缩放、旋转），和AutoCAD逻辑一致；块定义存在`BlockTable`。
- **标注Dimension**：存储**定义点（不是单纯绘制几何体）**：起点、终点、标注线位置、文字偏移；渲染时动态生成引线、箭头、文字。优势：修改模型，标注可以自动刷新。

> 不推荐：把标注直接炸成单纯线条，会丢失语义（BIM图纸联动必须保留标注语义）。

### 2. 二维几何基础、修剪Trim / 延伸Extend

Rust现有2D几何库可选：

1. **`geo` crate**：最成熟，点、线、多边形求交、裁剪、偏移；缺点：没有圆弧原生支持，只支持直线段。适合多边形，但**CAD圆弧/圆处理弱**。
2. **`kurbo`**：由Line/Arc/Bezier构成，支持圆弧求交，**非常适合CAD二维图元**，坐标f64，精度好，wgpu渲染友好。✅ 推荐首选。
3. **`euclid`**：向量、变换矩阵，配合kurbo做坐标变换。

#### Trim 修剪算法（CAD原生逻辑）

1. 拾取**切割边界** + 待修剪对象

2. 求待修剪图元和所有边界的交点，得到分割点集合

3. 判断拾取点在哪一侧，删除拾取侧的线段

   > 难点：圆弧、多段线分段处理；重叠交点、共线的容差判断（CAD必须有`eps`几何容差，比如1e-8）。

#### Extend 延伸算法

1. 拾取边界（目标边界）
2. 把选中图元无限延长（线/圆弧延长），求与边界的最近交点
3. 将图元端点移动至交点；无法相交则不执行。

> 注意：**所有2D几何运算必须带容差**，浮点精度问题是CAD类软件最大坑。

### 3. 对象捕捉 Snap（端点、中点、圆心、交点、垂足、最近点）

独立`snap`模块，思路：

1. 鼠标屏幕坐标 → 反变换到2D世界坐标
2. 在视口拾取框范围（屏幕像素阈值，例如5px），遍历**当前图层可见图元**
3. 依次计算候选捕捉点，计算距离，取最近点
4. 支持多种捕捉叠加（端点+交点同时开启）

```
enum SnapKind {
    EndPoint,
    MidPoint,
    Intersection,
    Center,
    Perpendicular,
    Nearest,
}
```

> 优化：空间索引（`rstar` crate）做2D空间分区，大图元集不要全量遍历，大幅提升拾取/捕捉性能。`rstar` 是Rust成熟R-Tree实现。

### 4. 文字、多行文字

- 字体：`ttf-parser` 解析ttf字体；`rustybuzz` 文字排版（复杂文本、换行）。
- 文字轮廓：`kurbo` 可以把文字转成贝塞尔曲线，用于矢量输出DXF；屏幕渲染可以用wgpu直接渲染文字纹理（`wgpu-text`）。
- 难点：CAD文字高度是**世界坐标单位**，不是像素；视口缩放时文字大小跟随图纸空间，可选支持注释性文字。

### 5. DXF读写（推荐优先DXF，放弃原生DWG）

Rust DXF crate：**`dxf`**（https://crates.io/crates/dxf）

- 支持 DXF R12、R2000+，读写图层、块、线、圆弧、标注、文字。
- 可直接序列化你内部`Entity2d`到DXF实体；反向DXF导入，映射回pvbim_2d的图元模型。
- 局限：对复杂标注、多行文字支持有部分缺失，可以fork扩展。

#### DWG怎么处理？

**不要手写DWG解析器**（Open Design Alliance ODA许可限制，商业风险高） 方案：

1. 导出DXF，外部工具（ODA File Converter）DXF→DWG，作为进程调用。
2. 或者用 ODA SDK 通过FFI调用（C binding），但增加项目复杂度，适合后期。

> 结论：开发阶段全部DXF；DWG作为可选导出产物，外部转换。

### 6. wgpu渲染二维视口（和你的三维BREP wgpu渲染共用渲染管线）

两个视口模式：

1. **模型空间（Model Space）**：三维投影生成的2D图元，无限大平面
2. **图纸空间（Paper Space / Layout）**：视口框（MVIEW），多图纸布局，打印比例

wgpu绘制2D：

- `kurbo`生成路径 → tessellate三角化（`lyon` crate），交给wgpu绘制线条/填充。
- 线条抗锯齿、虚线线型：lyon + wgpu可以实现；CAD虚线需要在世界空间，不能屏幕空间虚线。
- 图层控制：渲染前过滤`visible=false`图层；锁定图层仅不可编辑，仍然绘制。

> 三维BREP → HLR隐藏线 → 生成2D线框（可见线/隐藏线分层），输出到2D视口，这是你PVBIM的图纸核心链路。

### 7. 编辑命令系统架构

建议命令驱动架构，类似CAD命令栈：

```
trait Command {
    fn execute(&mut self, ctx: &mut DrawingContext) -> Result<()>;
    fn undo(&mut self, ctx: &mut DrawingContext) -> Result<()>;
}
```

- 维护Undo/Redo栈：每次修改图元集合，保存变更diff，不是全量保存图纸。
- 命令示例：TrimCommand、ExtendCommand、MoveCommand、DimensionCommand。

## 四、关键坑点（工程软件高频踩坑）

1. **浮点容差问题**：所有相交、捕捉、修剪不能直接`==`比较，统一全局几何epsilon（1e-6~1e-8）。
2. **标注关联性**：BIM场景，标注绑定三维模型投影点；模型变更自动更新标注位置。非关联标注作为备选。
3. **HLR隐藏线**：这是BIM出图最复杂部分。kurbo只负责2D，**HLR仍然是在你的Rust BREP内核做三维投影消隐**，输出2D图元给二维模块。不要指望2D库做消隐。
4. **图纸空间布局（Layout / MVIEW）**：图纸空间本质是多个相机视口，每个视口有独立比例，二维模块要分离模型空间与图纸空间两套坐标。
5. **性能**：图纸上万图元，R-Tree空间索引必不可少；编辑操作只做增量更新，不要每次重绘全量图元。

## 五、两条可选路线权衡

### 路线A（推荐，你的PVBIM路线）：自建轻量2D CAD模块（上面这套）

✅ 优势：

- 和你Rust BREP、wgpu原生打通，数据无缝，没有跨语言开销
- 只实现BIM出图必需子集：图层、块、标注、捕捉、trim/extend、DXF；不需要完整AutoCAD所有杂项实体
- 可控、可嵌入Tauri桌面端

❌劣势：

- 复杂高级功能（样条、复杂尺寸样式、参数化）需要自己写
- 没有现成完整CAD内核兜底

### 路线B：FFI绑定外部2D几何库（如libopencascade、libcad）

✅：省掉大量几何算法开发 ❌：Rust安全边界被打破，跨语言GC/内存坑；和wgpu渲染、你的Rust BREP集成麻烦，长维护成本高；**不推荐**。
