# 轻量化 BIM 内核平台 —— 立项基础方案（呈报稿）

[TOC]

> 文件性质：面向公司/部门领导的项目立项与资源调配建议书
> 撰写日期：2026-09-22　|　修订：v4（新增 cadrum 的 HLR 适用性源码级评估）
> 一句话定位：**做建筑与基础设施领域的"轻量化 BIM 内核平台"——第一阶段交付一个具备六大基础能力的通用 Core（B-Rep 存储管理 / HLR 显示 / CAD 平面图纸编辑 / 通用数据导入导出 / 几何构造 / 二次开发 SDK），专业功能（强电电气、暖通、给排水、弱电桥架、电缆隧道、电缆排管、电缆层支架、电缆排布、引上引下……）全部以 SDK 模块方式在第二阶段挂接。**
> 一句话补充：**不是做一款"电缆隧道专用软件"，而是做一套"能长出无数专业软件的底座"；也不是做"又一个轻量查看器"，而是要在二维出图上做到 Revit 级。**

## 〇、给领导的三分钟摘要

| 问题 | 回答 |
|---|---|
| 我们要做什么？ | 一个**通用三维 BIM 内核平台（Core）**：以 OCCT-WASM 为几何与出图主力，Rust 承担平台层、二维标注层与 SDK；**第一阶段只做"基础能力层"，不做专业功能** |
| 凭什么我们能做？ | 六大基础能力的技术路径清晰；几何内核有成熟的 WASM 集成方案可用，**把"从零自研几何内核"的千万元级投入替换为"集成成熟内核 + 自建平台层与 SDK"** |
| 解决谁的痛？ | 变电站、工厂、商业大楼等**多类建筑与基础设施**的三维正向设计；跨专业（强电电气 / 暖通 / 给排水 / 弱电桥架）协同；以及电力专业场景（电缆隧道 / 电缆排管 / 电缆层支架 / 电缆排布 / 引上引下） |
| 市场有多大？ | 中国 BIM 软件与服务为**百亿元级市场**并保持两位数增长；采购由**合规驱动**（国产 BIM 生态 + 三维正向设计 + 标准体系），需保留统计口径范围 |
| 要投入多少？ | 分两阶段：**第一阶段 Core 是平台研发预算**（六大能力 + SDK + Revit 级二维出图子集），**第二阶段专业模块以 SDK 方式增量开发** |
| 关键判断 | **几何内核选型决定一阶段能不能交付，SDK 生态决定二阶段能不能复利**；一阶段最大的范围风险是"二维出图做到 Revit 级" |

### 六大基础能力一览（第一阶段交付物）

| # | 基础能力 | 内涵 | 为什么必须先有 |
|---|---|---|---|
| 1 | **B-Rep 信息存储与管理** | 精确几何 + 拓扑 + 属性的组织、持久化、版本与事务管理 | 一切专业模块的数据地基，也是 GIM 对 DEV 层 B-Rep 解析的要求 |
| 2 | **HLR 显示能力** | 三维体到二维线框的消隐投影，供图纸级显示与输出 | 没有它只能做三维预览，无法产出可交付施工图 |
| 3 | **CAD 平面图纸编辑能力** | 二维图元的绘制 / 编辑 / 标注 / 图层，**目标对齐 Revit 的文档化能力** | 出图是作业链路真正稀缺的一环，不引入完整 CAD |
| 4 | **通用数据读取与导入导出** | **一阶段起码支持：IFC 解析、STEP 读写、DXF 兼容、glTF 解析** | 成果要能进得去、出得来，才能进入评审与移交 |
| 5 | **几何构造能力** | 拉伸 / 旋转 / 放样 / 布尔 / 倒角等建模算子 | 专业模块只做"业务装配"，几何算子由内核统一提供 |
| 6 | **模块二次开发 SDK** | 面向专业模块的插件接口、运行时与发布机制 | 第二阶段专业模块全部经 SDK 挂接，是"平台 → 生态"的关键开关 |

> **关于"内置元素"的边界（防止二阶段范围争议）**：Core 除上述六大能力外，还**内置一组跨专业共用的"基准定位元素"——轴网、标高、参考面、参考线**。它们是所有专业与所有视图共用的**定位地基**（构件靠"**标高 X 上的 Y 轴**"定位；平面 / 立面 / 剖面视图靠标高与轴网生成），因此**属平台基础设施，不归任何专业模块**。与此同时，**Core 不内置任何专业构件**（墙、柱、设备、电缆支架等一律由模块经 SDK 提供）。**把这条边界写清，可避免二阶段出现"轴网到底谁做"的扯皮。**（工程实现见设计文档 4.6）

### 三项本期新增的硬性要求（v3）

| 要求 | 结论 / 口径 |
|---|---|
| **几何内核选型** | **一阶段以 `occt-wasm` 为几何与出图主力**；**不采用 CADmium**（它是应用而非内核，且为 Elastic License 2.0）；`truck` 路线设观察位（见附录 A） |
| **二维出图目标** | **对齐 Revit 的文档化能力**：模型驱动的平立剖/详图 + 完整标注 + 图纸集 + 修订与显示控制（分解见附录 B），**这是本阶段最大的范围与成本风险点** |
| **数据互操作基线** | 一阶段四格式：**IFC 解析 / STEP 读写 / DXF 兼容 / glTF 解析**（IFC 是唯一 OCCT 不覆盖项，需独立组件） |

## 一、想法：这个项目到底在做什么

### 1.1 缘起

国家电网把 GIM 定义为"电网的 BIM 数据模型标准"，并在此之上建立了覆盖建模、协同、评审与移交的标准体系【19】。围绕三维设计成果的行业与团体标准已经成型，公开标准信息平台上可以查到电力行业三维设计成果移交、输变电工程三维协同设计以及电力电缆隧道设计规程等一系列编号标准【34】【33】。

这意味着一件事：**在电网系统内做三维设计工具，交付物的数据结构、精度分级与移交格式都是被规定好的，软件的自由度在"怎么建模、怎么出图"，而不在"用什么数据模型"。**

### 1.2 关键定位修正：不做"专用软件"，做"内核平台"

上一版方案把产品边界收敛在"电缆隧道"这一单一场景，这是**把平台层的能力误当成产品定位**。修正后的判断是：

> **应用场景远比电缆隧道宽——变电站、工厂、商业大楼等各类建筑与基础设施，专业上覆盖强电电气、暖通、给排水、弱电桥架等多个专业，电力侧还有电缆隧道、电缆排管、电缆层支架、电缆排布、引上引下等专业构件。如果把这些全部做进一个软件，就是又造一个"大而全、哪块都不深"的通用 BIM 平台，重蹈在位者的路径。**

因此本项目采取**两层架构**：

```
┌───────────────────────────────────────────────────────────┐
│  专业模块层（第二阶段起，全部经 SDK 挂接，可持续生长）        │
│   建筑专业：强电电气 / 暖通 / 给排水 / 弱电桥架 …            │
│   电力专业：电缆隧道 / 电缆排管 / 电缆层支架 / 电缆排布 /
│             引上引下 …                                     │
├───────────────────────────────────────────────────────────┤
│  平台 Core 层（第一阶段交付物，本期立项重点）                 │
│   ① B-Rep 信息存储与管理   ② HLR 显示能力                   │
│   ③ CAD 平面图纸编辑       ④ 通用数据读取与导入导出          │
│   ⑤ 几何构造能力           ⑥ 模块二次开发 SDK               │
└───────────────────────────────────────────────────────────┘
```

**第一阶段只做下面那一层，并且要做扎实；上面那一层是第二阶段的事，用 SDK 增量生长。**

### 1.3 核心思想（一句话）

**把"从零自研几何内核"的千万元级投入，替换成"集成成熟开源内核 + 自建平台层与 SDK"，从而把有限的工程人力集中到国产替代真正卡住的那一段——一套能做三维正向设计、能在二维出图上对齐 Revit、能被二次开发扩展的 BIM 内核。**

产品边界据此收敛为四条：

1. **主力几何存储采用精确 B-Rep**，三角网格只用于查看、校验与流转；
2. **几何与消隐运算交给成熟内核**（OCCT-WASM），不重复造轮子；
3. **二维出图是自建模块**，但对标的是 Revit 的文档化能力，而不是"能画线就行"；
4. **专业能力一律以 SDK 模块形式外挂**，内核不为任何单一专业做定制。

> **必须明确边界之外的判断**：纯网格主存储做正向设计、以及"从零自研纯 Rust 几何内核"这两条路线都**不采纳**。前者无法满足 GIM 对 DEV 层 B-Rep 解析的要求；后者会把项目拖进一个已有多个失败先例的长周期赛道（见 5.2），且无法在合理周期内交付 Revit 级出图。

### 1.4 技术底座（v3：依内核选型结论调整）

| 层 | 承担者 | 职责 |
|---|---|---|
| **几何核心** | **OCCT-WASM**（一阶段主力） | B-Rep 建模、布尔、放样/扫掠、倒角/抽壳、修复、**HLR 消隐**、STEP 读写、glTF 导出 |
| **平台与业务层** | **纯 Rust** | B-Rep 数据的组织与持久化、SDK 与插件宿主、二维标注层、专业模块运行时 |
| 渲染管线 | wgpu | 跨平台渲染（桌面 + 浏览器） |
| 语义层 | IFC4X3 + 自建数据模型 | 数据互操作与属性体系 |
| 互操作组件 | IfcOpenShell / web-ifc、dxf-rs、gltf crate | **IFC 解析**、DXF 兼容、glTF 解析（OCCT 不覆盖 IFC） |

> **与上一版的关键差异（须向领导讲清）**：v2 假设"Rust 内核承担主力建模、OCCT 仅承担 HLR"。本版依据新增要求（Revit 级二维出图 + 四格式互操作）**调整为一阶段以 OCCT-WASM 为几何与出图主力**，Rust 承担平台层与 SDK。
> **代价**：放弃"纯 Rust 工具链"这一卖点。
> **收益**：一阶段能够真正交付 Revit 级出图与四格式互操作，而不是在几何内核上无限期投入。
> 详见**附录 A：几何内核选型对比**。

## 二、模式：产品与技术模式

### 2.1 产品形态（三种终端）

| 终端 | 定位 | 承载能力 |
|---|---|---|
| **桌面端** | 主战场 | 大体量装配与出图 |
| **浏览器端** | 轻量协同 | 以 WebAssembly 承载几何内核，模型查看、轻量编辑与协同评审无需安装 |
| **服务端** | 后台支撑 | 模型转换、批量出图与项目级数据管理 |

### 2.2 平台化交付模式：Core + 模块 + SDK 三层

| 模式 | 面向对象 | 结算方式 | 说明 |
|---|---|---|---|
| **Core 授权** | 设计院、施工单位、软件厂商 | 按席位 / 按年订阅 | 提供六大基础能力与 SDK，是所有收入的底座 |
| **专业模块授权** | 有具体专业需求的客户 | 按模块 / 按年订阅 | 第二阶段起，强电电气、暖通、给排水、弱电桥架、电缆隧道等按需选购 |
| **SDK 生态** | 第三方开发者 / 行业厂商 | 授权费 + 生态分成 | 允许外部团队基于 SDK 开发专业模块，平台抽取生态价值 |
| **项目交付** | 具体工程的建模与成果移交 | 按项目结算 | **最容易在早期产生现金流，用于反哺平台与模块开发** |

> Core 只卖一次，模块与生态可以反复生长，这是平台型产品的复利来源。

### 2.3 开源合规是模式设计中不能回避的一环

本方案的几何核心是 OCCT，其 LGPL 系许可证义务边界在 GNU 官方问答与实务解读中表述明确：

- 静态链接 LGPL 库时，**必须提供应用自身的可重链接目标代码**，以便使用者替换库版本；
- 若自行随应用分发该库的可执行文件，仍须**随附该库源码**；
- 若库已存在于用户机器上而仅动态调用，则**无需随附源码**；
- 修改库本身则须以 LGPL 公开修改内容与日期，并在最终用户协议中去掉反逆向条款或增设例外【14】【15】【16】【17】。

> **`occt-wasm` 恰好是把这个合规问题部分解决的形态**：它把 OCCT 编译为 WASM 并在 wasmtime 沙箱内加载，属于"动态调用"而非静态链接，分发的是预编译 WASM 产物【46】。
> **但仍需注意**：crate 封装层为 MIT/Apache，底层 OCCT 本体仍是 LGPL-2.1+exception，**"分发 WASM 是否触发随附源码义务"必须在选型阶段由法务确认**，不能想当然。
> 此外，**CADmium 为 Elastic License 2.0（禁止作为服务对外提供）**【43】，因此不能作为产品底座，只能作为技术先例参考——许可证本身即构成排除项。

## 三、用途：核心应用场景

### 3.1 平台覆盖的"对象 × 专业"矩阵

| 维度 | 覆盖范围 |
|---|---|
| **建筑物类型** | 变电站、工厂、商业大楼，以及电缆隧道等基础设施 |
| **建筑与机电专业** | 强电电气、暖通、给排水、弱电桥架…… |
| **电力专业构件** | 电缆隧道、电缆排管、电缆层支架、电缆排布、引上引下…… |

> **平台只提供"通用能力"，上述矩阵中的每一格都由第二阶段的专业模块（SDK）去填充。**

### 3.2 三类通用用途（由 Core 直接支撑）

1. **三维正向设计**：几何数据以 B-Rep 保存，专业构件由模块装配到内核提供的几何与属性体系上。
2. **成果移交与评审**：软件按标准输出结构化模型与图纸，进入评审与移交流程。
3. **二维出图与施工交底**：由模型生成平、立、剖面图纸与节点详图，在二维图纸模块中完成标注与整饰。

### 3.3 作业链路与真正稀缺的环节

作业链路：**建模 → 校验 → 出图 → 移交**。

纯 Rust 的 B-Rep 生态普遍缺少 HLR 与轮廓提取能力，而 **HLR 是把三维体正确投影成二维工程图的必要步骤**；缺少它，软件只能做三维预览，无法产出可交付的施工图。

> **v3 结论**：正因为 HLR 与二维文档化能力是链路上真正稀缺、且自研周期极长的一环，本方案**直接采用 `occt-wasm` 提供 HLR 与几何运算**——它原生暴露 Hidden Line Removal 能力，并支持 STEP 读写与 glTF 导出【46】。

### 3.4 二维出图目标：对齐 Revit（本阶段最大风险点）

"CAD 平面图纸编辑要做到 Revit 的程度"是本方案范围最大的一项要求，必须先把"Revit 程度"拆解清楚，否则无法评估成本与验收。

> **核心认知**：Revit 的二维能力**不是"画二维图"，而是"模型驱动的视图 + 标注 + 图纸集"这一整套文档化层**。真正要复刻的是这个体系，而不是绘图工具本身。完整分解见**附录 B**。

| 层级 | 能力 | 优先级 |
|---|---|---|
| **视图体系** | 平面 / 立面 / 剖面 / 详图 / 大样（callout），由模型投影生成 | P0 |
| **标注体系** | 线性 / 对齐 / 角度 / 径向尺寸、高程点、标记（tag）、文字、引线 | P0 |
| **详图图元** | 详图线、填充区域、遮罩区域、符号 | P0 |
| **图纸与图框** | 图纸集、图框（title block）、视口、图例表 | P0 |
| **关联性** | 模型改动 → 视图与图纸自动更新 | **P0（本质）** |
| **显示控制** | 视图样板、可见性/图形替换（V/G）、图层/线型/线宽、对象样式 | P1 |
| **修订与校审** | 修订云线、修订表 | P1 |
| **明细表** | 明细表（schedule）与图纸联动 | P1 |

> **风险提示（必须让领导知道）**：上表 P0 部分已相当于复刻 Revit 的注释与文档层，工作量不低于几何内核集成本身，且**业内没有现成的开源实现对等物**。建议按 P0/P1 分期交付，先跑通"模型 → 视图 → 标注 → 图纸"闭环，而不是一开始就追求全量对齐。

## 四、价值：对客户、对公司

### 4.1 客户价值

| 价值点 | 说明 |
|---|---|
| **自主可控** | 图形、几何与出图能力完全落在自主可控的代码路径上，规避国际软件的授权与断供风险 |
| **一套底座、多专业复用** | 建筑、机电、电力多专业共享同一内核与数据格式，跨专业协同不再靠格式转换拼接 |
| **出图质量对齐主流** | 二维出图目标对齐 Revit，避免"三维好看、二维不能用"的低效困境 |
| **可扩展** | 专业功能以 SDK 模块形式交付，客户可只买所需模块，厂商与第三方都能持续扩展 |

### 4.2 公司价值（战略意义）

1. **以集成替代自研，压缩前期资金与时间门槛**：几何内核用成熟方案，资金风险从"能否造出来"转换为"能否用好现成构件"。
2. **用一段可控的工程投入换取一个有壁垒的技术位**：壁垒不来自通用几何能力——那需要十年以上的持续投入——而来自"**可出图的轻量化内核 + 可二次开发的平台 + 多专业模块生态**"这一组合。
3. **平台化带来复利**：Core 一次投入、模块反复生长；模块越多，平台越难被替代。
4. **卡位空档区**：通用厂商体量沉重；专业厂商普遍缺少底层几何与渲染的自主能力；**两者的空档就是本项目的位置**。

## 五、竞品：市场上有什么，我们差在哪、强在哪

### 5.1 竞品全景

| 类别 | 代表产品 | 能力 | 短板（我们的机会） |
|---|---|---|---|
| **国际通用 BIM 平台** | Autodesk Revit、Bentley 系列、ArchiCAD | 功能完整，第一梯队，**二维文档化能力即本项目对标对象** | 体量沉重、闭合生态；中国区报价未在公开渠道检索到可比数据 |

### 5.2 两份必须正视的反例证据

**技术侧的失败与半成品先例**：Fornjot 项目在运行约六年后由创建者关闭，说明**用 Rust 从零构建通用 CAD 内核的难度与周期远超预期**【11】；Truck 分支 monstertruck 曾以硬分叉方式回退一次布尔运算重写【2】【3】；CADmium 至 2024 年仍是"early prototype、not yet an MVP"，作者明确其目标是"用 10% 的工作覆盖 80% 的常见用例"【43】。

**在位者的财务证据**：恒华科技 2025 年年报显示亏损，并将原因归因于行业竞争加剧压缩利润与订单、新能源市场化改革降低投资热情、以及应收与合同资产计提减值【18】。

> 它说明在位者正承受激烈竞争与盈利压力，**新进入者面对的是价格战而非宽松市场**；但也说明**行业格局仍在变动之中**。

### 5.3 关键结论（可防守的表述）

> **通用 BIM 平台、轻量化 Web 编辑器与开源几何内核三者之间存在"组合能力空白"——即同时满足"精确 B-Rep 主存储 + 可交付 Revit 级二维出图 + IFC/STEP/DXF/glTF 四格式互操作 + 开放二次开发 SDK"的软件，目前尚无成熟产品。**
>
> 更准确地说：**在位者要么是封闭重型平台（有生态但不开放内核），要么是轻量编辑器（开放但只是工具、没有平台层与 SDK）**。本项目要做的是"**轻量化内核 + 开放 SDK + 对标 Revit 的出图层**"这一中间形态。

## 九、数学与技术背书

### 9.1 几何层：精确 B-Rep 与 NURBS

- **B-Rep** 用参数曲面与拓扑面、边、顶点的关联描述实体，精确表达解析曲面与自由曲面，**布尔与倒角、抽壳都定义在这一表示上**；
- **NURBS** 用带权控制点与节点向量统一表达直线、圆弧与自由曲线，是 STEP 等交换格式的基础表示。

> 这对应**能力①（B-Rep 存储管理）与能力⑤（几何构造）**。`occt-wasm` 直接提供这些算子，无需自研。

### 9.2 出图链路：HLR（消隐）

`occt-wasm` 在 I/O 与投影类目中**原生暴露 Hidden Line Removal（HLR）**能力，并提供 NURBS 数据提取、点/切向求值、插值等曲线能力【46】；OCCT 的消隐由视图计算模式驱动，精确路径以 `HLRAlgo_Projector` 与 `HLRBRep` 算法族实现轮廓与可见性判定【7】【8】；商用内核如 Spatial 的 CGM 也把 HLR 作为独立能力提供【9】。

> 这对应**能力②（HLR 显示）**，并直接支撑附录 B 的二维出图目标。
> **数值容差体系**：几何运算取 **1e-6 至 1e-8 量级**的 eps 用于点重合、面贴合与自交判定；过松误判相交，过紧让布尔运算在退化情形下失败。

> **选型前必须区分两个层级的 HLR（本方案的关键判据）**：
> - **预览级（渲染式消隐）**：在屏幕空间对**三角网格**做消隐，输出**折线 / 位图**，用于看图与快照；
> - **工程图级（精确消隐）**：基于 **B-Rep** 用 OCCT 的 `HLRBRep` 精确算法求轮廓与可见性，输出**可编辑的 2D 曲线实体**（圆仍是圆、弧仍是弧），供标注、尺寸与 DXF 出图。
>
> **本方案的出图目标（附录 B）要求的是后者。** 只提供前者的库，无论多轻量，都不能承担出图主力——附录 A.4 评估的 cadrum 即属前者。

### 9.3 数据互操作（能力④：四格式基线）

一阶段"起码支持"的四个格式，**难度与实现路径并不相同**，须分别设计：

| 格式 | 一阶段目标 | 实现路径 | 难度 / 风险 |
|---|---|---|---|
| **IFC** | **解析**（读构件、属性、空间层级） | **OCCT 不含 IFC**，需独立组件：IfcOpenShell【47】或 web-ifc【48】，或在 Rust 侧解析 IFC-SPF 并映射到自建数据模型 | **高**：本项目唯一在 OCCT 之外的能力，涉及语义映射与属性体系设计 |
| **STEP** | **读写**（含装配、颜色、名称、层级） | **`occt-wasm` 原生支持 import/export**，并经 XCAF 保留颜色/名称/装配层级【46】；备选 monstertruck 的 STEP 读写【45】 | **低** |
| **DXF** | **兼容**（二维图纸读写与常见图元） | Rust 生态：`dxf-rs`【12】、`acadrust`【13】 | **中**：块、图层、图元覆盖度需逐项验证 |
| **glTF** | **解析**（用于查看与流转） | `occt-wasm` 可导出 glTF；解析侧用 Rust `gltf` crate【49】 | **低–中** |

> **设计判断**：这四个格式构成"**评审入口（IFC）+ 交付通道（STEP）+ 出图通道（DXF）+ 查看流转通道（glTF）**"四条独立通路，缺一条就会在某个环节断链。**IFC 是唯一必须外购/自研的组件，也是本阶段互操作能力的成本与进度风险点。**

#### 9.3.1 能力④工作量清单：把"通用数据导入导出"从一句话落成可核算条目

能力④在能力表里只有一行字，却是六大能力中**格式最多、许可最杂、踩坑最分散**的一项。下面把每一项拆到"**要不要引库、引哪个库、怎么隔离、大概多少人月**"，作为排期与风险核算的依据。

| # | 子项 | 要否引入新库 | 选型 / 实现路径 | 许可与部署隔离 | 工作量口径 |
|---|---|---|---|---|---|
| ① | **二维投影（模型 → 视图）** | **否** | 三件套拼出：**视图变换矩阵** + **复用能力②的 HLR 投影结果** + **`kurbo` / `lyon` 绘制**。投影与消隐本质是同一件事的两半，**不另起炉灶** | 纯 Rust；`kurbo`（MIT / Apache-2.0）、`lyon`（MIT）【54】 | **中**：主要是视图 / 裁剪 / 比例体系 |
| ② | **制图国标与图纸语义层** | **否（自建规则引擎）** | 图幅、比例、线型线宽、图层、标注样式、会签栏、图纸集——**这些是"规则"不是"格式"**，必须自建一套可配置规则引擎 | 自研资产 | **高**：本能力④里最重的一段，与能力③出图强耦合 |
| ③ | **STEP / DXF / SVG** | **否** | STEP 走 `occt-wasm` 原生 + XCAF；DXF 走 `dxf-rs`【12】；SVG 用 `kurbo` / `lyon` 序列化（**零新依赖**）【54】 | 既有依赖 | **低**：翻译层为主 |
| ④ | **IFC4X3 导入** | **是** | `ifc-lite`（`ifc-lite-core`）或 `bimifc`（`bimifc-parser`），二者均**纯 Rust、MPL-2.0**；**先导入、后写回**，写回与否视实测覆盖度决定【51】【52】 | **MPL-2.0**：文件级 copyleft，**可静态链接、不污染自研代码**，但改动其源文件须回馈 | **中**：语义映射为主；**覆盖度须实测** |
| ⑤ | **DWG 导入** | **是（必须隔离）** | `LibreDWG`（GNU 项目，C 库，**GPLv3+**）；**只做导入、不做导出**；**必须放在独立的服务端进程 / 微服务中调用**，主程序不链接 GPL 代码【53】 | **GPLv3+ 有传染性 → 用进程边界隔离**（IPC 调用，主程序保持自有许可） | **中**：转换服务 + 进程隔离 |
| ⑥ | **GIM 解析** | **否（自建）** | 国网 GIM 为**非公开标准**，无可用开源解析器，**自建解析器**；按"电网侧专用模块"立项 | 自研资产 | **2–3 人月，单独排期**，不并入本期 Core |

> **一句话总结**：能力④真正"**要新买库**"的只有 **IFC（MPL-2.0，可静态链接）** 与 **DWG（GPLv3+，必须进程隔离）** 两项；**二维投影、制图国标、STEP / DXF / SVG、GIM 都不引入第三方库**——投影靠"变换矩阵 + 复用 HLR + kurbo / lyon"，国标靠自建规则引擎，GIM 靠自建解析器。
>
> **许可红线（写入合规评审）**：`occt-wasm`（LGPL-2.1，WASM 动态形态）、`ifc-lite` / `bimifc`（MPL-2.0）、`LibreDWG`（GPLv3+）三者许可强度**依次升高**，其中 **GPLv3+ 那一项只能靠进程隔离兜住**——**绝不可把 LibreDWG 静态链接进主程序**。
>
> **对"工作量"的口径修正**：本表把能力④的绝大部分工作量落在 **②制图国标规则引擎** 与 **⑥GIM 解析** 上，而非"格式转换"本身；**格式转换是低风险翻译层，规则引擎与私有标准解析才是成本热点**——这与 10.2 风险清单中"出图范围"为 P0 的判断一致。

### 9.4 渲染层与平台架构

- 基于 W3C 的 WebGPU 规范，着色器语言为 WGSL，可在同一套代码下覆盖桌面与浏览器【39】【40】；
- **几何计算与渲染解耦**：几何在 WASM 内核侧完成，渲染只消费网格与轮廓数据；更换内核实现时渲染层无需改动；
- **SDK 与插件边界（能力⑥）**：OCCT 以 WASM 沙箱隔离，专业模块通过 SDK 注册几何算子、属性模式与**二维标注规则**，**内核不感知任何具体专业**；
- **性能策略**：大装配几何分解为可并行任务；桌面端多线程、浏览器端 Worker，把 WASM 模块加载与计算放到渲染主线程之外；`OcctKernel` 实例按 worker 线程复用（创建慢、单次调用快）【46】。

## 十、落地路线图与风险边界

### 10.1 分阶段推进（v3 调整验收标准）

| 阶段 | 目标 | 验收标准 |
|---|---|---|
| **第一阶段：Core** | 交付**六大基础能力 + SDK 框架** | ① 能用内核完成几何构造与 B-Rep 存储；② **四格式基线可用：IFC 可解析、STEP 可读写、DXF 可兼容、glTF 可解析**；③ 能经 HLR 生成二维图纸并完成"模型→视图→标注→图纸"闭环（附录 B 的 P0 子集）；④ 能经 SDK 挂接一个最小示例模块 |
| **第二阶段：专业模块** | 用 SDK 交付首批专业模块 | 电力侧：电缆隧道、电缆排管、电缆层支架、电缆排布、引上引下可用；建筑侧：强电电气、暖通、给排水、弱电桥架至少各有一个可用模块 |
| **第三阶段：工程交付与生态** | 完成首个实际工程交付并开放 SDK 生态 | 在真实项目中完成建模、出图与移交全链路；引入至少一个第三方团队基于 SDK 开发模块 |

> 三个阶段**把技术不确定性与商业不确定性分开验证**：一阶段验证"内核与平台能不能立住、SDK 接口对不对、出图能不能对齐"；二阶段验证"模块化能不能长出专业能力"；三阶段才验证"客户愿不愿意用、生态能不能起来"。
> **一阶段若 SDK 接口或二维出图 P0 子集失败，后面全盘皆输**，因此本期重点不是模块数量，而是**接口质量 + 出图闭环**。

### 10.2 风险清单（按严重度排序）

| 优先级 | 风险 | 说明 | 应对 |
|---|---|---|---|
| **P0** | **二维出图对齐 Revit 的范围风险** | 附录 B 的 P0 子集工作量不低于内核集成，且**业内无现成开源对等物** | 严格按 P0/P1 分期；先交付"模型→视图→标注→图纸"闭环，不追求全量对齐 |
| **P0** | **IFC 组件缺失** | OCCT 不含 IFC，必须另配 IfcOpenShell / web-ifc 或自研解析 | 一阶段即立项 IFC 组件选型；**把 IFC 解析作为独立里程碑**，不与几何进度绑定 |
| **P0** | **SDK 接口设计失误** | 接口若贴合单一专业，二阶段无法低成本扩展 | 用 1–2 个示例模块验证接口通用性；接口以"几何算子 + 属性模式 + 标注规则"抽象 |
| **P0** | **LGPL 在 WASM 分发下的义务** | `occt-wasm` 动态加载降低但**未消除**合规不确定性【14】【15】【16】【17】【46】 | 交付前由法务确认"分发 WASM 是否触发随附源码"；建立合规检查点 |
| P1 | 性能风险 | OCCT-WASM 计算密集约为原生 2 倍，大装配可能不达标 | 桌面端优先原生路径（如条件允许）；大装配并行分解；设定性能基线并持续 benchmark |
| P1 | 上游维护风险 | monstertruck 单人维护；brepkit 部分布尔回退网格且转 AGPL-3.0-only【2】【3】【4】 | **不采用为关键路径**，仅设观察位 |

| P1 | 范围蔓延风险 | 定位放宽到多专业后，易把二阶段内容提前塞进 Core | 严守"Core 只做六大能力"边界 |
| P2 | 人员风险 | 团队规模小，同时覆盖几何、渲染、平台与多专业 | 一阶段聚焦内核、SDK 与出图，专业模块由模块团队/第三方分担 |

## 十一、结论与请示事项

### 11.1 结论

1. **定位修正成立**：本项目**不是"电缆隧道专用软件"，而是"轻量化 BIM 内核平台（Core）+ 专业模块 SDK 生态"**，覆盖变电站、工厂、商业大楼等建筑与基础设施及多类专业。
2. **内核选型有明确结论**：**一阶段以 `occt-wasm` 为几何与出图主力**（原生提供 HLR、STEP 读写、glTF 导出）；**不采用 CADmium**（应用而非内核，且 Elastic License 2.0）；`truck` 路线仅设观察位。**这一结论使方案放弃"纯 Rust 工具链"卖点，换取一阶段可交付性。**
3. **出图目标是最大风险点**："二维出图做到 Revit 级"等价于复刻 Revit 的注释与文档层，**业内无开源对等物**，必须按 P0/P1 分期交付。
4. **互操作基线可达成但有一处硬缺口**：STEP / DXF / glTF 均低风险；**IFC 是 OCCT 不覆盖的唯一缺口**，须独立选型（IfcOpenShell / web-ifc / 自研解析）。
5. **风险清晰**：P0 风险为**出图范围、IFC 组件、SDK 接口、LGPL 合规**四项，均已在 10.2 列明应对。

### 11.2 请示事项（资源倾斜建议）

| 事项 | 建议 |
|---|---|
| **立项** | 批准立项，先做**第一阶段 Core（六大能力 + SDK 框架 + 出图 P0 子集 + 四格式基线）** 的可行性原型 |
| **人力** | 组建小型团队，围绕**内核集成、平台层与 SDK、二维出图层、互操作组件**四块配置 |
| **口径** | 对外统一为"**轻量化 BIM 内核平台（Core + SDK）**"；**不宣称"自研几何内核"，不宣称"纯 Rust 工具链"** |
| **决策点** | 一阶段验收（四格式可用 + 出图闭环 + SDK 可挂接示例模块）通过后，再批准进入二阶段 |
| **法务** | **立项即启动 LGPL 在 WASM 分发下的合规确认**，作为里程碑而非收尾事项 |
| **范围约束** | 明确"Core 不含任何专业功能"；出图严格按 P0/P1 分期 |

## 附录 A：几何内核选型对比（truck / CADmium 路线 vs occt-wasm）

### A.1 先纠正一个前提

> **CADmium 不是几何内核**，它是一个**应用 + Rust 库（`cadmium`）**，其底层 B-Rep 内核是 **`truck`**【43】。因此本对比的实质是：
> **「truck 纯 Rust 路线（以 CADmium 为代表应用）」 vs 「occt-wasm（OCCT 的 WASM 形态）」**。
> 把 CADmium 当成内核选项，会在一开始就选错比较对象。

### A.2 逐项对比

| 维度 | truck 路线（CADmium 为代表） | **occt-wasm** | 判定 |
|---|---|---|---|
| **实质定位** | 应用 + 库；内核为 truck | OCCT 的 WASM 封装，**完整 B-Rep 内核能力** | occt-wasm 胜 |
| **项目状态** | CADmium 早期原型（"not yet an MVP"），面向爱好者，目标"10% 工作覆盖 80% 用例"【43】 | 已发布多个稳定版（3.3.x），170+ 方法，生产可用度较高【46】 | occt-wasm 胜 |
| **几何能力** | NURBS、布尔（and/or）、fillet、healing、assembly【45】 | 基元 / 布尔（含 history）/ 放样 / 扫掠 / fillet / chamfer / shell / offset / draft / thicken、修复、演化历史【46】 | occt-wasm 胜 |
| **HLR（出图必需）** | **不提供** | **原生提供** | **occt-wasm 决定性胜出** |
| **STEP 读写** | 提供（ISO 10303-21，件与装配）【45】 | 提供（XCAF，含颜色/名称/装配层级）【46】 | 相当，occt-wasm 略优 |
| **glTF** | 非内核能力（经 three.js 渲染） | **原生提供 glTF 导出** | occt-wasm 胜 |
| **IFC** | 不支持 | 不支持 | 均需外部组件 |
| **二维出图** | 草图可导出 SVG / DXF【43】 | HLR 线框可驱动二维出图 | occt-wasm 胜 |
| **渲染栈** | three.js / WebGL（Threlte），非 wgpu【43】 | 不绑定渲染，与 wgpu 解耦 | occt-wasm 更契合本方案 |
| **Rust 集成** | 纯 Rust，直接嵌入，无跨边界开销 | 经 wasmtime 加载，跨边界约 2 倍开销【46】 | truck 胜 |
| **性能** | 原生 Rust，轻量 | 计算密集约 2 倍原生开销；首次加载 100–500ms【46】 | truck 胜 |
| **许可证** | CADmium **Elastic License 2.0（禁止作为服务对外提供）**【43】；truck 本体 MIT/Apache | crate 为 **MIT/Apache**；底层 OCCT 为 **LGPL-2.1+exception**【46】 | 各有约束；**CADmium 直接出局** |
| **维护风险** | truck 由 RICOS 维护但生态年轻；monstertruck 自述"研究矿脉，非生产可用"，单人维护风险【2】【3】 | OCCT 上游数十万行长期维护 + 活跃封装者【46】 | occt-wasm 胜 |
| **Linux 支持** | Truck 手册明确"Linux 尚未正式支持"【44】 | WASM 与平台无关 | occt-wasm 胜 |

### A.3 选型结论

| 结论 | 内容 |
|---|---|
| **一阶段主力** | **采用 `occt-wasm`**：它一次性覆盖能力②（HLR）、能力⑤（几何构造）、能力④中的 STEP 与 glTF，**是一阶段唯一能交付 Revit 级出图的现实选项** |
| **不采用** | **CADmium**——① 它是应用不是内核；② Elastic License 2.0 禁止作为服务对外提供；③ 其内核 truck 不提供 HLR |
| **观察位** | **truck / monstertruck**：轻量、纯 Rust、无 C++ 依赖，适合"浏览器端轻量预览"与"长期自主化"两条支线，**但不进一阶段关键路径** |
| **架构含义** | 方案由 v2 的"Rust 内核主力 + OCCT 仅做 HLR"调整为"**OCCT-WASM 为几何/出图主力 + Rust 平台层/SDK/标注层**"。**放弃"纯 Rust"卖点，换取一阶段可交付性** |
| **遗留风险** | 性能约 2 倍开销、首次加载延迟、桌面嵌入方式、LGPL 在 WASM 分发下的义务——四项须在一阶段逐项验证 |

### A.4 补充评估：cadrum 能否负责 HLR（源码级结论）

> **结论先行：不能作为"工程图级 HLR"的主力；只能作为"预览 / 快照级消隐"的第二实现或对照。**

`cadrum` 是一个 Rust CAD crate，**静态链接 headless OCCT 8.0.1**，可原生运行亦可编译到 `wasm32-unknown-unknown`；本体 MIT，内嵌 OCCT 为 LGPL 2.1【50】。它确实提供消隐输出（`Mesh::scene(SceneOption { hidden_edges, .. })` → `Scene2D::write_svg` / `write_png`），但**源码层面**（`e:/WORKSPACE/CODE_RUST/cadrum`）暴露出三处硬约束：

| # | 事实（源码定位） | 对"Revit 级出图"的影响 |
|---|---|---|
| 1 | **消隐在 Rust 侧基于三角网格实现**：`detect_silhouette_edges` 从三角形邻接提取轮廓边，`classify_edges` 用 `is_point_occluded(mid, …)` **逐线段取中点**判定遮挡（`src/common/mesh.rs`）；而 `src/ffi.h` / `src/ffi.cpp` 的 FFI 面**未包装 `HLRBRep` / `HLRAlgo`** | 属**网格级、屏幕空间消隐**，非 OCCT 精确 HLR；隐藏线断点精度受网格密度限制，跨遮挡边界的线段会误判 |
| 2 | **2D 场景只取轮廓边**：`Mesh::scene` 注释明确拓扑边 `self.edges` 是 "for glTF export only"，SVG / PNG 管线 "derives its own view-dependent silhouette set" | 输出为**离散轮廓折线**，不含拓扑边的精确曲线语义 |
| 3 | **输出即二维折线**：`Scene2D { edges_visible: Vec<DVec2>, edges_hidden: Vec<DVec2> }`，NaN 分隔；可调参数仅 `view / up / hidden_edges / shading` | **无 ARC / CIRCLE / SPLINE 实体**，圆被离散为折线 → 无法标注半径/直径、无法捕捉圆心、DXF 只能导 LWPOLYLINE；**无剖切面 / 视图深度 / 平立剖详图体系** |

**许可证维度尤其关键**：cadrum **静态链接 OCCT**，其 README 明确要求"分发基于 cadrum 构建的应用须遵守 LGPL 2.1，终端用户必须能重建并重新链接 OCCT"【50】——这正是本方案 2.3 节所担心的**静态链接 LGPL 义务**。`occt-wasm` 以 WASM 动态加载，恰恰规避了它。**故在合规维度上，cadrum 比 occt-wasm 更差而非更好。**

| 用途 | 结论 |
|---|---|
| 一阶段 Core 的**工程图级 HLR 主力** | ❌ 不采用（网格级消隐 + 折线输出 + 无图纸视图） |
| **预览 / 快照级消隐**（模型 → SVG/PNG 视图，供评审与 LLM 设计回路） | ✅ 可用，且性能路线优于 occt-wasm（原生静态链接，无 2 倍 WASM 开销） |
| **长期自主化**参考（纯内存运算 + `wasm32-unknown-unknown` 构建链） | ⚠️ 构建方案可参考，但许可证与出图能力均不满足要求 |

> **前置条件提醒**：若 `occt-wasm` 暴露的 HLR 同样停留在"返回折线 / 位图"层级，则**也不足以**支撑 Revit 级出图。**选型阶段必须核实其 HLR 返回的是精确 2D 曲线（`Geom2d_Curve`）还是折线——这是附录 B 出图目标能否成立的前置条件。**

## 附录 B：二维出图"Revit 级"目标分解

### B.1 为什么不能只说"做到 Revit 的程度"

> Revit 的二维能力 = **模型驱动的视图系统 + 标注系统 + 图纸集 + 修订与显示控制 + 明细表**。
> 它不是"绘图工具"，而是**一套与三维模型强关联的文档化层**。
> 因此"做到 Revit 的程度"必须拆成可验收的条目，否则无法评估工作量与进度。

## 附录 C：一句话电梯陈述
